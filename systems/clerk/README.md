# Clerk

A measured reference for Clerk’s signed-in web dashboard, captured on 2026-10-30 from a Hobby workspace and its existing development application. Dark captures cover the main dashboard and settings; light captures cover email/password settings, the password requirements dialog, Users and workspace settings. Public authentication landing-page screenshots are separate marketing references.

Dashboard readings record actual CSS viewport widths of 390, 884, 1440 and 1600. Not every page was captured at every width. The owner signed in through the Codex in-app browser and approved the appearance change for the light capture. The original dark theme was restored and verified afterward. No user was created, no invitation sent, no application configuration saved, and no destructive confirmation submitted.

## How the values were read

The capture reads computed styles on real DOM elements and custom properties from the document root. Each reading records its actual viewport, element index, class, rectangle, state and measured properties. These readings stay distinct from screenshots: the browser screenshot path reflows some layouts, so DOM rectangles cannot safely select screenshot crops. The crop builder accepts only visually checked native screenshot coordinates.

The token builder maps declared CSS properties and observed element values into core scales and the captured dark and light sets. Raw measurements remain available under [raw/readings/](raw/readings/). Usage counts count observations across capture states, including repeated appearances of the same control, rather than unique production elements. Color string normalization preserves the measured value; the package does not invent missing scales or uncaptured theme states.

Images were inspected, email addresses masked using native-pixel OCR boxes, and then quantized to 256 colors. The screenshot ingestion record lists accepted and excluded captures. Raw screenshots and any private text remain outside git under the operator’s capture scratch directory. Ordinary names, avatars and owner content remain under this repository’s private-reference policy.

## What to distrust

- **Limited light coverage.** Five light states cover email/password settings, the password requirements dialog, Users and workspace settings at a measured 884 CSS-pixel width. Light mobile, all other light pages and matching light interaction states remain uncaptured. The public light landing page is a separate product surface.
- **Widths describe readings.** Requested browser dimensions, actual CSS dimensions and output PNG dimensions differ under the browser’s current zoom. Use recorded CSS measurements for values and screenshots for composition, not pixel-to-CSS arithmetic.
- **Partial interaction coverage.** Default, selected, disabled, open menu/dialog and one keyboard-focus state were sampled. Hover, pressed, loading buttons, submission validation and post-save feedback are not measured.
- **Focus wrapper gap.** The password field screenshot shows a focus ring, but the measured input reports no painted outline. Its surrounding wrapper was not measured, so no focus-ring width is asserted.
- **Full-page modal context.** A modal backdrop covers its viewport; full-page captures can show unblurred content below it. Use the complete dialog crops for component shape. The clipped mobile create-user modal is excluded.
- **Public animations are examples.** The landing-page authentication and dashboard demos rotate automatically. They are marketing examples, not evidence of actual signed-in states.
- **Limited roles.** Declared CSS values are not proof that every component uses them. Surface refers to the observed header; status ramps, semantic completeness and component behavior require further capture.
- **No exhaustive product crawl.** API-key and test-credential screens, paid activation flows, financial details, all user profiles and every nested settings tab were excluded or left uncaptured. Existing application settings were inspected without saving changes; only the approved appearance switch was changed and restored.

## Do and don't

- **Use a compact persistent header with a separate page navigation row.** Keep application and environment selectors grouped; do not scatter them through the page. [Overview](screenshots/overview-dark-desktop.png).
- **Separate settings into named groups with helper text.** Keep the control aligned with its description; do not flatten every option into a dense table. [Email settings](screenshots/authentication-email-dark-1440.png).
- **Reserve the purple filled treatment for the primary action.** Keep cancellation and secondary actions quiet. [Password dialog](screenshots/password-requirements-dialog-dark-desktop.png).
- **Keep table tools above the rows.** Put search and column choices in the toolbar and show a useful empty message inside the table. [Users](screenshots/users-dark-desktop.png) and [empty logs](screenshots/logs-empty-dark-desktop.png).
- **Explain consequences in confirmation dialogs.** Keep the cancel action available beside the destructive action. [Disable confirmation](screenshots/disable-native-confirmation-dark-desktop.png).

These are observed layout rules for this reference, not published Clerk design principles. Borrow structure and proportions; do not ship Clerk branding, icons or proprietary assets.

The capture functions in [tools/capture-repl.js](tools/capture-repl.js) run through the documented Codex computer-use API after the owner selects and signs into the browser tab. They are not a script for attaching to another browser or transferring a session. Fresh ingestion needs the original external capture directory; token, component and guide rebuilds use committed sanitized readings. Review privacy and screenshot framing before accepting new captures. Run the builders twice and compare output bytes.
