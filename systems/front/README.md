# Front design reference

A token set and component reference for Front's public surfaces — for building customer-support-platform marketing pages, pricing grids, help-centre chrome and a product auth shell in the style of the real thing. It was read from **front.com** on **2026-11-16**, signed out, in headless Chromium at 1440 x 900 and 390 x 844. Captured: front.com's home page, /pricing, /product, /product/omnichannel-support-inbox, /product/ai, /customer-service, /customer-stories (+ the Uber Freight story), /integrations, /compare/front-vs-intercom, /industries/b2b-tech, /teams/customer-service-support, /resources, /blog (+ one article), /glossary, /about, /reviews, /download, /security, /request-demo, /signup and /whats-new; the header's Product, Solutions and Resources mega menus; the pricing billing switch and FAQ disclosures; app.frontapp.com's /signin, /signup and /forgot-password auth cards **in light and in the shell's own dark theme**; help.front.com's home, one article and the contact page; dev.frontapp.com's docs and reference; and 390px passes on home, pricing, sign-in and help. A **2026-11-21** public walk added [site-tree.md](site-tree.md) and empty-wall shots of `https://app.frontapp.com/signin` in light and dark at 1440 and 390. That walk typed nothing and submitted nothing. The map of which control opens which page is [site-tree.md](site-tree.md). The empty wall is [login-review.json](login-review.json).

Front is worth a capture because it paints **four different design stacks** on its public web. The marketing site is a Next.js + Tailwind app whose design layer is compiled into bespoke classes — hue-utility ramps (`.bg-violet-50..1000`, `.bg-citron-*`, `.bg-blue-*`, `.bg-gray-*`…), a semantic surface scale (`.surface-l0..l3`, `.surface-highlight`, `.surface-outer`), a type ramp (`.text-display1` 62px down to `.text-micro*`) and a button state layer (`.button-primary-*`, `.button-size-*`) — each redeclared under **three section themes**: `[data-theme="theme-dark-violet"]` (the signature plum), `theme-white` and `theme-gray`. There is no page-level theme switch; sections alternate. The product SPA's auth shell is the opposite: a real custom-property layer — 332 resolved `--color-*` variables (primitive ramps plus bg/text/icon/border/input/accent semantics) that redeclare under `html[data-theme="dark"]`, driven by the `front-theme-preference` localStorage key — captured both ways, and the dark pass verifies the attribute actually painted. help.front.com is Front's own Knowledge Base product and dev.frontapp.com a ReadMe portal; both embed Front's Companion/Froyo token sheet (`@layer tokens`, ~1,342 declarations of `--colors-*`/`--sizes-*`/`--spacing-*`/`--radii-*`/`--font-*`/`--shadows-*`/`--easings-*`/`--durations-*` with light and dark semantic repointings). Four self-hosted voices on the marketing site: **Suisse Intl** for everything, **Suisse Intl Mono** for figures and code, **Suisse Works** for serif display; the app shell sets **Indivisible**. **Boundary:** the signed-in workspace was never reached — every CTA, SSO button and nav link was measured, never followed; the demo, signup, auth and search fields were typed into then cleared, never submitted; the Qualified "Quinn" widget was measured and screenshot at rest, never opened.

## Brief

<!-- brief:start. Generated by tools/brief.py from catalog.json, the tokens file and this README; `make brief` rewrites it. Do not edit. -->

Read this before designing in this style. Take every value from [tokens.json](tokens.json), never from the screenshots; `python3 tools/catalog.py export front` prints them all with aliases resolved.

### Principles

1. Do pick the token set of the stack you are building.
2. Do let plum and citron carry the brand.
3. Do spend violet on the action.
4. Do set the app shell in Froyo terms.
5. Don't style the signed-in workspace from this package.
6. Don't treat the marketing sets as a dark mode.
7. Don't fabricate form outcomes.
8. Don't copy the brand.

Each rule links the screenshot or crop that shows it, under [Do and don't](#do-and-dont).

## What to distrust

- **The signed-in product.** The workspace — inbox, contacts, rules, analytics, settings — needs an account this capture does not have. app.frontapp.com's auth shell *is* the product's real token layer, but it is only the login edge; nothing here describes the workspace. The `/signup` and `/forgot-password` routes paint the same card as `/signin` (email + password + "Sign in"), honestly labelled.
- **The marketing "themes" are section themes.** `violet`, `light` and `gray` are the three `[data-theme]` contexts the marketing site's own stylesheets ship; sections alternate them on one page. There is no user switch and no marketing dark mode — the `dark` set is the app auth shell's, a different stack.
- **The companion sets are an embedded layer.** `companion`/`companionDark` are the Froyo token sheet's `--colors-*` semantics as shipped to help/dev pages — the product design language in transit, not the help page's own paint (that is `help`). dev.frontapp.com's own `--color-*` overrides are ReadMe vendor values, kept in `raw/css-vars.json` under `vendor`, not promoted to tokens.
- **The forms.** The 2026-11-16 pass typed demo, signup, auth and search fields, then cleared them. The 2026-11-21 walk left every field empty. Validation, error, loading and success states are unverified because nothing was submitted.
- **Reduced motion is mostly ignored.** The probe found the marketing pages keep their transitions under `prefers-reduced-motion: reduce` (`raw/motion.json`); do not assume motion-off variants exist.
- **Quantised screenshots.** `screenshots/` are 256-colour PNGs; read exact colours from tokens or the raw values, never the pixels.

## Do and don't

1. **Do pick the token set of the stack you are building.** `violet`/`light`/`gray` are the marketing section themes, `app`/`dark` the auth shell, `companion`/`companionDark` the Froyo messenger layer, `help` the Knowledge Base — same role names, different paints. See [tokens.json](tokens.json) and [help-light-default](screenshots/help-light-default.png).
2. **Do let plum and citron carry the brand.** The marketing hero sits on `violet.surface.l0` #300c41 behind `violet.text.primary` #f8f1fe; the citron `violet.surface.highlight` #dee948 is the accent reserved for the CTA. White and gray sections stay quiet — `light.text.primary` #0d1d39 ink, hairline `core.palette.gray.200` borders. See [hero-cta](components/crops/hero-cta-default.png) and [home-light-default](screenshots/home-light-default.png).
3. **Do spend violet on the action.** `light.button.surface` #8034bf is the primary button fill on light sections; on plum sections the same role repaints to citron. Secondary actions stay bordered, ink-on-surface. See [nav-try](components/crops/nav-try-default.png) and [plan-cta](components/crops/plan-cta-default.png).
4. **Do set the app shell in Froyo terms.** The auth card reads `app.color.bg.surface.primary.default`, `app.color.bg.fill.brand.default`, `app.color.text.*` — resolved values, not the marketing palette; its dark pass is the same token names under `dark.color.*`. See [appd-panel](components/crops/appd-panel-default.png).
5. **Don't style the signed-in workspace from this package.** Only the auth edge was captured — the inbox, contacts, rules and settings were never reached. See [signin-light-default](screenshots/signin-light-default.png).
6. **Don't treat the marketing sets as a dark mode.** `violet` and `gray` are section themes on one light page; the `dark` set is the app's own `data-theme="dark"` repaint, a different stack. See [signindark-dark-default](screenshots/signindark-dark-default.png).
7. **Don't fabricate form outcomes.** The 2026-11-16 pass typed demo, signup, auth and search fields, then cleared them. The 2026-11-21 walk left the sign-in wall and the demo and trial dialogs empty. Validation, error and success states are unverified. See [demo-email](components/crops/demo-email-filled.png) and [signin-light-empty](screenshots/signin-light-empty.png).
8. **Don't copy the brand.** Suisse faces, the Front mark and the Qualified widget are the product's assets; borrow proportions and roles, not artwork. See [mkt-logo](components/crops/mkt-logo-default.png) and [home-light-widget](screenshots/home-light-widget.png).
