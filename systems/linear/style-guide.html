Brief

Read this before designing in this style. Take every value from tokens.json, never from the screenshots; python3 tools/catalog.py export linear prints them all with aliases resolved.

Principles

  1. Do keep the pale filled pill for the one main action.
  2. Do keep color in small marks.
  3. Don't use one rounded rectangle for everything.
  4. Don't carry marketing scale into dense screens.
  5. Don't replace mixed filled and outlined glyphs with a uniform arbitrary stroke.
  6. Do draw focus as a 1px outline in the focus colour.

Each rule links the screenshot or crop that shows it, under Do and don't.

How the app values were read

The owner signed in to linear.app in the Claude desktop app's browser pane; nothing was typed for them. Each state (a page, a menu open, a tooltip shown, a toast after "Copy issue URL") was copied with tools/capture/signed-in/snapshot.js, which inlines every stylesheet, scripts removed. Linear keeps its theme in a constructed stylesheet (document.adoptedStyleSheets), which the kit's snapshot did not copy, so this package's copy of the script inlines it too. The same script scrubs private text before the copy leaves the browser: issue, project and description text become "Sample issue N", "Sample project N" and "Sample text N", identifiers become CORE-N, and avatar and workspace images become a grey disc. unsnap.py refused any copy in which a redacted string survived. The copies stay outside the repository.

Headless Chromium then read the copies offline: tools/capture/vars.mjs read every CSS variable with getComputedStyle on <main>, and tools/capture/signed-in/measure.mjs read 47 components with real pointer hover, real keyboard focus (focus-visible) and the mouse held down (pressed). Results: raw/css-vars.json, raw/components-computed.json, raw/measurements.md, crops in components/crops/.

Linear applies its theme on .theme-provider-<hash> wrappers; :root only carries dark fallback values. Reading :root in a light page returns dark colours, so every theme value here was read inside the provider. Linear computes its palette in lch(); the builder converts to sRGB hex with the CSS Color 4 formulas, so a channel can differ by one from a hex Linear declares elsewhere (the focus ring computes to #5e6ad2, Linear's fallback hex is #5e69d1).

The account theme was Dark. For the light copies the Interface theme setting was switched to Light with the owner's agreement and set back to Dark afterwards; no other setting, issue or record was changed. Widths: 1440 for every page, 390 for the board and an empty state. Font size: Default.

What to distrust

Status colours depend on the team's workflow; feedback.warning is the "At risk" health label, a muted text colour, not a warning banner (none appeared); the checkbox is invisible in the copies (script shows it on row hover), so only its 12px box was read; avatar fills are this package's grey disc, only their size and shape are Linear's.

Some crops do not show the state their name gives. Keyboard focus reached the board card, the sub-issue row and the description editor, but nothing changed in the copies: raw/components-computed.json reads outline none, and card-focus-visible, list-row-focus-visible and text-area-focus-visible (both themes) are byte-identical to their default crops. Whether the live app marks focus on these some other way is not known. The hover crops of the card and the toast are also identical to their defaults, with no computed change.

No disabled control appeared, so text.quaternary is the faintest text colour, not a confirmed disabled colour. The focus offset differs by control (see Do and don't 6), so core.focusRing.offset-button (2px) fits primary buttons and the switch only; the secondary and destructive buttons measured 0. The redraws button-primary-disabled.svg and field-error.svg show states this capture never reached.

Do and don't

  1. Do keep the pale filled pill for the one main action. The header's Sign up and a single hero or plan action (Get started, Talk to sales, Watch example) are pale #E5E5E6 pills with dark text; the action beside them is a dark pill, and section links are muted text with an arrow or plus ("Learn more →", "Projects +"). See 01-home, pricing and startups.
  2. Do keep color in small marks. In the product demos, status, priority and label color sits in a small icon, dot or short health word, while issue titles, ids and row backgrounds stay white or gray. The #5E6AD2 accent appears only in demo details (the composer send button, the @mention, the billing toggle, chart fills); the site's own buttons and links in these screenshots never use it. See 01-home, enterprise, plan and pricing.
  3. Don't use one rounded rectangle for everything. Pill actions, modestly rounded sidebar items, squared list rows and more rounded floating surfaces serve different roles. The homepage shows all four at once: the Sign up pill, the 8px selected sidebar row, flat issue rows and the floating agent panel. See 01-home.
  4. Don't carry marketing scale into dense screens. Public pages use large whitespace, narrow text measures and oversized editorial titles (64px homepage hero, 128px Tiempos on Method) that do not belong in a dense issue table. The product demos on the same pages keep 13px sidebar text and one-line issue rows. See 01-home and method.
  5. Don't replace mixed filled and outlined glyphs with a uniform arbitrary stroke. The demo sidebar sets outlined glyphs (Inbox, Projects) beside filled ones (the Agent Insights bars, the solid arrow inside Initiatives) and a half-filled status circle. See 01-home.
  6. Do draw focus as a 1px outline in the focus colour. On every button, link, text and search field, select, switch, tab and sidebar item measured, focus-visible is 1px solid #5E6AD2 (dark) or #6D78D5 (light), with the control's own shadow unchanged. The offset depends on the control: 2px outside primary buttons and the switch, 0 on secondary, destructive and icon buttons, the property chip and the select, 1px on links, -1px inside text fields, tabs and sidebar items. The board card, sub-issue row and description editor showed no ring in the copies (see What to distrust). See button-primary-focus-visible and text-field-focus-visible.

Import into Figma, Paper or another vector editor

Import any boards/*.svg file for a full reference sheet, or components/*.svg for isolated pieces. In Figma, drag the SVG files onto the canvas. In Paper or another editor, use its SVG import/paste support if available; the exact Paper workflow has not been tested here. The SVGs use ordinary paths, rectangles, text and named groups, with no foreignObject, linked fonts or raster UI embedded.

These are vector assets, not a native .fig library. Import does not automatically create component variants, auto-layout, variable bindings or prototype interactions; text editability depends on the importer. Convert the imported groups to components and configure variants in the destination tool if needed. components/manifest.json gives intended names and bounds.

tokens.json uses DTCG $type/$value tokens in five sets (core, dark, light, web, brand), colours as sRGB hex, each with $extensions.source and $extensions.evidence. tokens/tokens-studio.json has the same sets with plain values for Tokens Studio. Import with a token-aware plugin/tool that supports that format; neither file is claimed to be a native Figma variables import. tokens/linear.css supplies CSS custom properties, dark on :root and light under [data-theme="light"]. Preserve the evidence fields when promoting tokens into a production design system.

The SVG syntax and browser rendering are checked locally. Import into Paper/Figma itself is unverified. Font installation and commercial font licenses are not included.
