# Capy desktop design reference

A token set and component reference for Capy's desktop app for macOS (Scrapybara, bundle id `ai.capy.desktop`), version 0.4.7 (Electron 44.3.0, Chrome 152), captured on 2026-10-25 from the owner's signed-in account (a personal workspace with no plan). Capy runs coding agents in the cloud: a thread starts from one composer on a project's GitHub repositories (or on a paired Mac), and the app around it is the thread list, pull requests, automations, Memory, Drive and about twenty Settings panes. The app shell, every Settings pane, the menus, the search palette and Capy's own component gallery were captured in Capy's light and dark themes, at the window size the app was in: 1280 x 800 pt. The agent run was taken later the same day, once the owner had connected Claude Code as a model provider; by then Capy had updated itself to 0.5.0, so the run's frames are 0.5.0's (see [What to distrust](#what-to-distrust)).

The window is the capy.ai web app inside a desktop frame. Capy 0.4.7 does not load https://capy.ai over the network: its bundle carries the web app's build (`Contents/Resources/renderer`, 63 MB, 1,179 assets, whose shell page names capy.ai as its URL) and serves it over its own `capy://app/` scheme, so the same React app runs from the bundle and talks to `api.capy.ai`. `app.asar` holds only the Electron main process and preloads. What the desktop shell adds is listed under [The desktop shell](#the-desktop-shell).

Everything was read live from the running app over Chromium's remote-debugging port, with Playwright connected over CDP, using the route the [cursor-desktop](../cursor-desktop/README.md) pilot built for the Electron coding harnesses in [issue 107](https://github.com/c-wenlong/designs/issues/107): full-window screenshots of every screen and state, every custom property the stylesheets declare as it computes and paints, and the computed style of every captured part in every state. Use it to build a calm, dense agent app: an off-white or near-black window with a rounded content panel set into it, Inter at 13px, hairline edges at 0.5px, text tiers mixed from one ink, and one teal accent for starting work and for on-states.

This package contains no Capy code or artwork beyond the app icon (`icon.png`); the screenshots and the visual system they show are Scrapybara's ([docs/RIGHTS.md](../../docs/RIGHTS.md)). Borrow structure and proportions, not the brand.

## Brief

Read this before designing in this style. Take every value from [tokens.json](tokens.json), never from the screenshots; `python3 tools/catalog.py export capy-desktop` prints them all with aliases resolved.

### Principles

1. Do set the content on a rounded panel inside the window.
2. Do mix the muted text from the ink, not from grey hexes.
3. Do lift surfaces with a hairline, not a blur.
4. Do keep teal for starting work and for on-states.
5. Do paint destructive actions red, and only them.
6. Don't colour selection.

Each rule links the screenshot or crop that shows it, under [Do and don't](#do-and-dont).

## How the values were read

Capy is an Electron app (`Contents/Frameworks/Electron Framework.framework`), so its interface is HTML and CSS. It was not running; it was opened with `open -a Capy --args --remote-debugging-port=9407`, which it accepted on the first launch, and Playwright attached with `chromium.connectOverCDP`. The account was already signed in inside the app; nothing was typed into a sign-in screen. The one window is a CDP page at `capy://app/...`, titled Capy (Settings pages are titled `<pane> | Capy`). The capture scripts are the pilot's, in [tools/capture/electron/](tools/capture/electron): [cdp.mjs](tools/capture/electron/cdp.mjs) connects, [shots.mjs](tools/capture/electron/shots.mjs) drives the shot list in [product.mjs](tools/capture/electron/product.mjs), [vars.mjs](tools/capture/electron/vars.mjs) reads the custom properties and [run.mjs](tools/capture/electron/run.mjs) captures an agent run; Capy adds [frame.mjs](tools/capture/electron/frame.mjs) (the native window) and [gallery.mjs](tools/capture/electron/gallery.mjs) (the gallery's notes). Screenshots are CDP's `Page.captureScreenshot`.

**The theme.** Capy is built with Tailwind CSS 4 on Base UI (`data-slot` names on every part). Its theme is about forty oklch seeds on `:root, [data-theme-preview]` and on `.dark` in the app stylesheet: the window (`bg`, which `chrome` repeats), the content panel, card, popover, input and button fills, the ink (`fg`, `text`), the teal `primary`, `destructive`, `warning`, `success`, `info`, four hues, diff and eight chart colours. Everything else is a `color-mix()` of those, declared under `@supports (color: color-mix(in lab, red, red))` with a plain `var()` fallback: the three muted text tiers are the text mixed into the window colour (62, 48 and 36% in light; 68, 52 and 38% in dark), the soft fills a seed at 18 to 30% over transparent, the link and the ring the primary darkened with black. Tailwind's `--color-*` names are all `var()` aliases of these seeds; no Tailwind palette is loaded beyond black and white. [build_tokens.py](tools/build_tokens.py) keeps a seed as its painted sRGB value, makes a name an alias when its declaration is a plain `var()` of a name that paints the same, and otherwise keeps the painted colour with the formula beside it. The five shadow levels (`--sh-plate`, `--sh-card`, `--sh-overlay`, `--sh-composer`, `--sh-sheet`) are read from their computed text, because vars.mjs paints only names containing `shadow`.

**Themes.** Capy's Theme setting (Settings > Appearance) is System, and its System theme follows `prefers-color-scheme`. CDP's `Emulation.setEmulatedMedia` switched `<html>` between `.light` and `.dark` at once, so each pass ran with the scheme emulated (`SCHEME=light` or `SCHEME=dark`) and Capy's own setting was never touched. Capy painted light when it opened although macOS was in its dark appearance; with the emulation it followed either. Capy also ships fourteen colour themes besides its default (Absolutely, Bearded OLED, Catppuccin, Codex, Crimson Evernight, Everforest, Firecrawl, GitHub, Gruvbox, Hub, Linear, Notion, One, and a custom one) as `[data-color-theme]` overrides; only the default was captured.

**Two places.** The app on the owner's account (New thread, Threads, Pull requests, Automations, Memory, Drive, every Settings pane, the menus, the palette, Customize sidebar), where nothing was sent, created or changed; and Capy's component gallery at `capy://app/design`, which ships in the bundle but is not linked from the app's navigation. The gallery's own title is "Every component in the system, on the surface it ships on": about fifty sections of Capy's real components on fixture data, each specimen beside a one-line note (Avatar: "A rounded square, never a circle"). The owner's own threads were never opened, so the thread view, its tool calls, the destructive confirmation and the toasts come from the gallery, and their screenshots say so in [patterns.md](patterns.md). [gallery.mjs](tools/capture/electron/gallery.mjs) copied the notes into [raw/design-gallery.json](raw/design-gallery.json).

**Components and states.** Each shot resets the window to the New thread page (or to the gallery section it needs), reveals one state with Capy's own hooks (`data-slot` names, roles, aria-labels, never account text), takes the screenshot and reads the computed style of every listed part, recording its box for [crops.py](tools/crops.py). Hover is a real pointer over the part, focus-visible real keyboard focus (a key press, then `focus()`): Capy draws its own focus outline, a 1px `base.ring` line just inside the edge, so nothing was switched on. Pressed is `:active` forced through CDP's `CSS.forcePseudoState` with the pointer over the part, never a click. Before and after every shot the script compares the new-thread draft, its project, the model, the colour theme, the Run on choice and the desktop tabs (all in the window's localStorage) and stops if any changed.

**The agent run.** The owner approved test prompts on 2026-10-25 in a fresh thread only, on a throwaway folder ([docs/CAPTURE.md](../../docs/CAPTURE.md#the-scratch-folder-for-test-prompts)). The first pass could not start one: the organization limited models to connections that were not set up, so Start came back with Failed to start thread ("Copilot is not connected, connect it to use Claude Opus 5.5"). Later that day the owner connected Claude Code in Settings > Models, and the run was taken again on Capy 0.5.0.

Cloud threads now open a plan dialog ("Put Capy to work", Capy Lite, Pro and Max), since the account has no plan, so the run goes to the paired Mac. The capture made a project of its own, Capture scratch, from the folder `~/.design-systems/harness-scratch/capy/` (a git repository holding one README commit), with New project > Folder on a machine; Capy runs its threads in that folder itself (Run on: the Mac, Current checkout, no worktree). [run.mjs](tools/capture/electron/run.mjs) picks that project and refuses to start unless Run on names that folder on this Mac. In a new thread it sends "List the files in this folder." and then "Create hello.txt here with one line.", and finally opens the thread's right pane.

It screenshots the window every 500 ms and records the run's state from Capy's own markers: the Stop run button, the tab's Working glyph, a live shimmer on a work row, and a reply after the last prompt. [quantize.py](tools/capture/quantize.py) then keeps one frame per state. The model is the one the owner's composer held, Claude Haiku 5.5 through Claude Code. No approval prompt appeared: the agent listed the folder and wrote hello.txt without asking, and no permission setting was changed to make it ask.

**What the capture changed, and put back.** The composer's project went to Scratchpad and back three times, and the owner's unsent draft was cleared and typed back each time (the stored draft is identical). The 2026-11 audit changed the restore (edited, not run): typing a draft with a line break presses Enter, which would submit the composer and start a real thread, so `RUN.finish` now writes the saved draft back to localStorage and reloads instead (`tools/capture/electron/draft.mjs`). Each theme opened one extra desktop tab and closed it, opened and cancelled menus, the palette and Customize sidebar, and typed into Settings search and cleared it. Visiting pages wrote Capy's own view state to localStorage (list filters, sort orders, the model picker's last tab, the tab history, one pane entry per refused thread); at the end every key was set back to the snapshot taken before the capture, except the home-project cache, which names the same project with a higher write count. One thing differs and was not put back: the composer's Run on label read Cloud and 2 repos when Capy opened, and reads the paired Mac with New worktree and 1 of 2 repos since the project was switched back; Capy's stored Run on choice is unchanged (`{}`) and no Run on option was picked. Capy was quit at the end and not reopened.

**What the run changed, and put back.** Between the two passes the owner set Scratchpad's Run on to the Mac and the model to Claude Haiku 5.5; both were left as the owner set them. A first attempt on Scratchpad in the cloud opened the plan dialog and created nothing. The run created the Capture scratch project and four threads in it, all left for the owner to delete: CAPT-1 (a probe), CAPT-2 (dark), CAPT-3 (a light run whose second prompt went out before the first had finished, discarded) and CAPT-4 (light). The agent wrote `hello.txt` in the scratch folder. Each theme switched the composer's project to Capture scratch and back to Scratchpad, and Capy's view state (thread panes, desktop tabs) was set back to the snapshot taken before the run, except the home-project cache's write count. The owner's unsent draft, cleared by the first attempt, was typed back. Capy was quit and not reopened.

## What to distrust

- **The run is Capy 0.5.0; everything else is 0.4.7.** Capy updated itself between the first pass and the run. Read again on 0.5.0, the theme paints the same 129 colours in both themes; the custom properties gained 29 declarations (a `.pele` chart theme made of existing tokens, `--z-preview-guest`) and dropped `--text-5xl`, which `core.fontSize.5xl` still holds from 0.4.7. tokens.json keeps the 0.4.7 readings, and the other screens were not taken again.
- **The thread view has two sources.** The run frames (`run-*.png`) and every part in a run state (`working`, `thinking`, `tool`, `streaming`, `done`) are the app; the `conversation`, `tool-rows`, `device-access`, `delete-confirmation` and `toast` screens, and the conversation parts in `default`, are Capy's components on fixture data at `capy://app/design`.
- **The paired Mac's name is painted out.** Capy shows the owner's Mac as a paired device (the composer's Run on picker, the Run on menu, the Machine picker under a thread's composer, Settings > Devices, the audit log); it is the Mac's network name, so it is painted over in every screenshot and crop, which leaves a grey smear where the name was. The gallery's fixture addresses for named people, its fixture pairing code and its fixture one-time code are painted too. The rules are in [tools/redact-rules/capy-desktop.json](../../tools/redact-rules/capy-desktop.json).
- **The model name is amber in the 0.4.7 screens.** The composer draws `claude-opus-5-5` in `base.warning-fg` because no connection in this account could serve it then; the run frames show Claude Haiku 5.5, served by Claude Code, in the plain text colour.
- **The Run on label changed during the capture.** Light and dark screens show the paired Mac and 1 of 2 repos in the composer where Capy first showed Cloud and 2 repos; see [How the values were read](#how-the-values-were-read).
- **Component values are one element each.** `component.*` and components.md read the first element that matched each part (or the shot [prefer.py](tools/prefer.py) names); they are not counts across pages.
- **Light cards have no border.** `base.card-hairline` is transparent in light, so light cards are lifted by `shadow.card` (a 0.5px ring) and dark cards by a `base.border-1` hairline; the dark-only border values are in `dark.$extensions.notTokenised`.
- **The bundle may not match capy.ai today.** The renderer in the bundle is the build that shipped with 0.4.7; the website may have moved on.
- Screenshots are 256-colour PNGs. Flat UI colours are exact; read values from tokens.json.

## Do and don't

1. **Do set the content on a rounded panel inside the window.** The tab strip and the sidebar sit on the window colour (`base.chrome`); every page is a `base.panel` inset with the 12px radius and a 0.5px edge, a step lighter than the window in both themes. See [home](screenshots/light/home.png) and [settings-general](screenshots/dark/settings-general.png).
2. **Do mix the muted text from the ink, not from grey hexes.** The three secondary tiers are the text colour mixed into the window colour at fixed shares, so they move with the theme. See [settings-capy](screenshots/light/settings-capy.png) and [settings-capy dark](screenshots/dark/settings-capy.png).
3. **Do lift surfaces with a hairline, not a blur.** Cards and the active tab carry a 0.5px ring in light (`shadow.card`) and a `base.border-1` edge in dark; only menus, the composer, dialogs and toasts cast a soft shadow. See [card](components/crops/card-default-light.png), [card dark](components/crops/card-default.png) and [tabs-two](screenshots/dark/tabs-two.png).
4. **Do keep teal for starting work and for on-states.** Start, the accent button, switches and checkboxes when on, the count chip and Update are `base.primary`; page actions are ghost, outline or soft. See [button-accent](components/crops/button-accent-default.png), [switch-on](components/crops/switch-on-default-light.png) and [settings-notifications](screenshots/dark/settings-notifications.png).
5. **Do paint destructive actions red, and only them.** The confirmation's Delete thread is the red fill beside a ghost Cancel; Delete and Log out in menus are red text. See [delete-confirmation](screenshots/dark/delete-confirmation.png) and [thread-context-menu](screenshots/light/thread-context-menu.png).
6. **Don't colour selection.** A selected or hovered row takes a soft wash (`base.secondary`) and the full ink, never the accent. See [nav-row-selected](components/crops/nav-row-selected-default.png) and [thread-row-hover light](components/crops/thread-row-hover-light.png).

## Rebuild

From the package folder:

```bash
python3 tools/build_tokens.py && python3 tools/build_style_guide.py && python3 tools/build_components_md.py
```

`build_tokens.py` reads `raw/css-vars.*.json` and `raw/components.*.json` and writes `tokens.json`; it refuses a token without a source, an alias that points at nothing, a dimension that is not one length and a colour that is not hex or rgba, and moves a name present in only one theme to `$extensions.notTokenised`. `build_style_guide.py` renders `style-guide.html` from `tokens.json`; `build_components_md.py` writes `components.md` from the readings, `tokens.json` and the crops. All three are deterministic, standard library only. `python3 tools/crops.py` (needs Pillow) cuts `components/crops/` from the screenshots.

To capture again (Capy must not be running; Playwright from `~/.design-systems/pw`). The owner's account must be signed in with a model connected, and the capture expects the New thread composer to hold the owner's draft (or none). `run.mjs` also expects the project Capture scratch (`RUN_PROJECT`) on `~/.design-systems/harness-scratch/capy/`, running on this Mac; make it once with New project > Folder on a machine:

```bash
open -a Capy --args --remote-debugging-port=9407
export PORT=9407   # SLUG defaults to this package's folder name
SCHEME=dark  KEEP='^--(?!tw-)' node tools/capture/electron/vars.mjs raw/css-vars.dark.json Capy body
SCHEME=dark  node tools/capture/electron/shots.mjs dark
SCHEME=dark  node tools/capture/electron/frame.mjs dark
SCHEME=dark  INTERVAL=500 node tools/capture/electron/run.mjs dark
SCHEME=light KEEP='^--(?!tw-)' node tools/capture/electron/vars.mjs raw/css-vars.light.json Capy body
SCHEME=light node tools/capture/electron/shots.mjs light
SCHEME=light node tools/capture/electron/frame.mjs light
SCHEME=light INTERVAL=500 node tools/capture/electron/run.mjs light
node tools/capture/electron/gallery.mjs raw/design-gallery.json
```

`vars.mjs` picks the window by its exact title, so run it on the New thread page (titled Capy). `shots.mjs` runs before `run.mjs` in each theme, so the composer screens show the owner's draft; `run.mjs` puts the project and the draft back even when a step fails. Then quit Capy (`osascript -e 'tell application "Capy" to quit'`), run `python3 tools/capture/quantize.py ~/.design-systems/capy-desktop/raw-shots`, which also copies the readings into `raw/` and converts the native window captures from Display P3, apply [the redaction rules](../../tools/redact-rules/capy-desktop.json) with `tools/redact_images.py apply` (with the local pattern file that names the paired Mac), and run `tools/crops.py` and the builders. [quantize.py](tools/capture/quantize.py) picks the run frames by the state `run.mjs` recorded for each (`RUN_FRAMES`) and keeps the parts each frame is the best view of (`RUN_PARTS`); look at the picks after a new run. It stores every screenshot again from the raw captures, so the redaction step must follow it.
